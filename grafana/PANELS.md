# 패널별 상세 — `manyak-server-overview`

각 패널이 **무엇을 보기 위한 것인지, 단위가 무엇인지, 어떤 사건이 값을 움직이는지, 어떻게 읽는지**를 정리합니다. 대시보드 설계 배경과 예산·쿼리 규칙은 [`README.md`](./README.md)에 있습니다.

## 읽기 전에 알아야 할 공통 사항

**모든 쿼리에 `service_name="$service"`가 붙습니다.** 운영은 `manyak-server`, 로컬은 `manyak-server-local`입니다. 라벨 이름이 `job`이 아닌 이유는 README의 쿼리 규칙 절에 있습니다.

**시간 해상도는 60초입니다.** OTLP export step이 60초라 원본 데이터 포인트가 분당 하나입니다. `rate(...[5m])`은 그 5개 점 위에서 계산되므로, **1분 미만의 짧은 스파이크는 대시보드에 나타나지 않습니다.** 짧은 사건을 봐야 하면 로그나 Sentry를 봐야 합니다.

**`rate(...[5m])`는 5분 이동평균입니다.** 사건 발생 직후 값이 바로 튀지 않고 몇 분에 걸쳐 올라갔다가, 사건이 끝나도 5분간 꼬리가 남습니다. 그래프의 시작·끝 시각을 사건의 시각으로 읽으면 안 됩니다.

**`histogram_quantile`은 근사값입니다.** 버킷 경계 사이를 선형 보간하므로 정확한 분위수가 아닙니다. 특히 값이 히스토그램 상한을 넘으면 마지막 버킷(`+Inf`)에 몰려 **상한 근처 숫자로 뭉개집니다.** 각 메트릭의 상한은 아래 패널별 항목과 README의 히스토그램 상한 절에 있습니다.

**`outcome`이라는 태그가 두 종류입니다.** 이게 가장 헷갈리는 함정입니다.

| 메트릭 | `outcome` 값 | 누가 붙이나 |
| --- | --- | --- |
| `http_server_requests_*` | `SUCCESS` · `CLIENT_ERROR` · `SERVER_ERROR` · `REDIRECTION` (대문자) | Spring Boot 자동 |
| `manyak_ai_call_duration_*` | `success` · `failure` (소문자) | `AiCallRecorder` |
| `manyak_story_creation_duration_*` | `success` · `failure` · `rejected` (소문자) | `SimpleStoryCreationService` |
| `manyak_storyline_creation_result_*` | `success` · `failure` · `rejected` (소문자) | `SimpleStoryCreationService` |

**이름이 같을 뿐 전혀 다른 축입니다.** 대소문자로 구분되며, 섞어 쓰면 조용히 빈 결과가 나옵니다. 아래 셋(소문자)은 의미가 같으니 함께 읽어도 됩니다.

# RED — 요청률 · 오류율 · 응답시간

서비스가 밖에서 어떻게 보이는지를 다루는 층입니다. 이상 징후를 **가장 먼저 발견하는** 곳이지, 원인을 찾는 곳은 아닙니다.

## 요청률 (req/s)

```promql
sum(rate(http_server_requests_milliseconds_count{service_name="$service"}[5m]))
```

| | |
| --- | --- |
| 단위 | `reqps` — 초당 요청 수. Y축 최소 0 |
| 출처 | Spring Boot 자동 계측(`http.server.requests`). 별도 코드 없음 |
| 재는 구간 | 컨트롤러 진입부터 응답 완료까지. 요청이 **끝나야** 카운트됩니다 |

**무엇을 보나** — 트래픽의 절대량이 아니라 **모양**을 봅니다. 다른 모든 패널의 해석이 이 값에 달려 있습니다. 요청이 거의 없는 시간대의 p95나 오류율은 표본이 적어 신뢰할 수 없기 때문입니다.

**값을 움직이는 것**

- 실제 사용자 유입 — 마케팅, 앱 푸시, 외부 유입
- **헬스체크와 Actuator** — `/actuator/health`가 주기적으로 호출되면 트래픽이 0이어도 바닥값이 깔립니다. 신규 배포 직후 이 바닥값만 보이는 게 정상입니다
- 프론트엔드 폴링이나 재시도 루프 — 사용자 수와 무관하게 요청만 늘어납니다
- 배포로 인스턴스가 재시작하면 카운터가 0부터 다시 시작하지만, `rate`는 리셋을 감지해 보정하므로 **가짜 급감으로 보이지 않습니다**

**읽는 법** — 급증보다 **급감이 더 위험한 신호**입니다. 요청이 0에 수렴하면 서버가 아니라 그 앞단(로드밸런서, DNS, 프론트엔드 배포 사고)이 깨졌을 수 있고, 이 경우 5xx 오류율은 오히려 깨끗해 보입니다.

**함정** — 이 값은 **전체 합계**라 어느 엔드포인트인지 모릅니다. `uri`별로 쪼개려면 Explore에서 `sum by (uri) (...)`로 봐야 합니다. 대시보드에 상시로 두지 않은 이유는 엔드포인트가 40개라 legend가 읽을 수 없게 되기 때문입니다.

## 5xx 오류율 (%)

```promql
100 * (sum(rate(http_server_requests_milliseconds_count{service_name="$service", status=~"5.."}[5m])) or vector(0))
    / clamp_min(sum(rate(http_server_requests_milliseconds_count{service_name="$service"}[5m])), 0.0001)
```

| | |
| --- | --- |
| 단위 | `percent` — 0~100. Y축 최소 0 |
| 임계선 | 1% 주황 · 5% 빨강 (색상 표시용이며 **알림이 아닙니다**) |
| 출처 | Spring Boot `status` 태그(HTTP 상태 코드 문자열) |

**무엇을 보나** — 서버 책임으로 실패한 요청의 비율입니다. **4xx는 일부러 뺐습니다.** 없는 리소스 요청이나 권한 없는 접근은 서버가 정상 동작한 결과이고, 클라이언트 버그나 크롤러 때문에 얼마든지 늘어나므로 서버 건강도 지표로 쓸 수 없습니다.

**값을 움직이는 것**

- AI 호출 실패·타임아웃이 502로 나가는 경우 — **가장 흔한 원인**
- 처리되지 않은 예외(500)
- DB 커넥션 고갈이나 쿼리 타임아웃
- 배포 직후 기동이 덜 끝난 상태에서 들어온 요청
- **분모가 작아져서** — 트래픽이 거의 없는 새벽에 5xx 한 건이면 비율이 크게 튑니다

**읽는 법** — 절대 비율보다 **요청률 패널과 함께** 봐야 합니다. 새벽에 20%가 떠도 요청 5건 중 1건일 수 있습니다. 지속적으로 1%를 넘으면 실제 문제이고, 5%를 넘으면 사용자가 체감하는 수준입니다.

**함정 — 0%와 `No data`는 다릅니다.** 5xx가 한 건도 없으면 분자 시계열이 아예 생성되지 않고, 빈 벡터를 나누면 결과도 비어 화면에는 `No data`가 뜹니다. 오류가 없는 것과 수집이 끊긴 것이 똑같이 보이는 셈입니다. 그래서 `or vector(0)`으로 0을 명시적으로 그립니다. **이 패널이 진짜 비어 있으면 수집 장애를 의심해야 합니다.**

분모의 `clamp_min(..., 0.0001)`은 트래픽이 완전히 0인 구간에서 0으로 나누는 것을 막습니다.

**같이 볼 것** — 값이 올랐다면 AI 실패율 패널을 먼저 봅니다. 거기가 함께 올랐으면 원인이 AI이고, 깨끗하면 AI 밖(DB·크레딧·직렬화)입니다.

## HTTP p95 (ms)

```promql
histogram_quantile(0.95, sum by (le) (rate(http_server_requests_milliseconds_bucket{service_name="$service"}[5m])))
```

| | |
| --- | --- |
| 단위 | `ms` — 밀리초. Y축 최소 0 |
| 히스토그램 구간 | **10ms ~ 10s** (`application.yml`) |
| 출처 | Spring Boot 자동 계측의 `_bucket` 시계열 |

**무엇을 보나** — 느린 쪽 5%가 얼마나 기다리는지입니다. 평균이 아니라 p95를 쓰는 이유는, 평균은 빠른 조회 요청 다수에 희석돼 느린 소수를 감춰 버리기 때문입니다.

**값을 움직이는 것**

- AI를 기다리는 엔드포인트의 비중 — 이게 지배적입니다
- GC 정지 — 힙 압박이 심하면 모든 엔드포인트가 함께 느려집니다
- DB 커넥션 대기 — HikariCP `pending`이 0이 아닌 상태
- **트래픽 구성 변화** — 서버는 그대로인데 느린 엔드포인트 호출 비중만 늘어도 p95는 오릅니다
- 같은 인스턴스의 AI 컨테이너가 CPU를 점유하는 상황

**읽는 법 — ⚠️ 이 패널의 상한은 10초입니다.** AI 완성을 기다리는 요청은 수십 초가 걸리는데, 히스토그램 상한이 10초라 그 요청들은 전부 마지막 버킷에 몰립니다. **즉 AI 대기 엔드포인트가 조금만 섞여도 이 값은 10초 근처에 붙어 버리고, 거기서부터는 더 느려져도 그래프가 안 움직입니다.**

이건 버그가 아니라 의도한 선택입니다. HTTP 상한을 올리면 늘어난 버킷이 엔드포인트 수만큼 곱해져 시계열 예산을 크게 잡아먹습니다. **AI 경로의 지연은 아래 전용 타이머로 봅니다.**

**함정** — `uri` 태그는 경로 템플릿(`/api/v1/stories/{publicId}`)입니다. 매칭되지 않은 요청은 `NOT_FOUND`나 `UNKNOWN`으로 묶이는데, 이 안전장치가 없으면 임의 경로 스캔만으로 시계열이 무한히 늘어납니다.

# AI 호출

`AiCallRecorder`라는 **공통 호출 경계 한 곳**에서 계측합니다. 새 AI 기능이 늘어도 이 경계를 지나므로 계측이 빠지지 않습니다.

재는 구간은 **manyak-server가 manyak-ai를 호출한 왕복 전체**입니다. LLM 시간만이 아니라 컨테이너 간 네트워크와 AI 서버 자체 처리가 포함됩니다. Langfuse와의 역할 차이는 README를 보세요.

## AI 호출 p95 (feature별, ms)

```promql
histogram_quantile(0.95, sum by (le, feature) (
  rate(manyak_ai_call_duration_milliseconds_bucket{service_name="$service", outcome="success"}[5m])))
```

| | |
| --- | --- |
| 단위 | `ms` — 밀리초 |
| 히스토그램 구간 | **100ms ~ 240s** — compile 타임아웃 180s보다 위 |
| 필터 | `outcome="success"` — **성공 호출만** |
| 분할 | `feature`별 (4종) |

**무엇을 보나** — 외부 AI가 얼마나 느린지입니다. 이 서비스에서 지연의 지배적 요인이고 우리가 통제하지 못하는 외부 의존입니다.

**`feature` 값과 각각의 타임아웃**

| `feature` | 타임아웃 | 성격 |
| --- | --- | --- |
| `storyline_generation` | read 90s | 스토리라인 후보 3개 생성 |
| `story_completion` | read 180s | 본문 완성. **가장 오래 걸립니다** |
| `chat_response` | stream 60s | 채팅 턴 응답 |
| `choice_generation` | choices 90s | 선택지 생성 |

connect timeout은 공통 5초입니다. **연결 자체가 안 되는 장애는 5초 안에 실패로 떨어지므로, p95가 아니라 실패율 패널에 나타납니다.**

**성공만 재는 이유** — 실패에는 타임아웃(정확히 90초나 180초)과 즉시 실패(5초 이내 연결 거부)가 섞여 있습니다. 이 둘을 성공과 한 분포에 넣으면 p95가 실제 응답 성능이 아니라 실패 구성비를 반영하게 됩니다.

**값을 움직이는 것**

- DeepSeek 등 LLM 제공자의 지연 — 대개 우리와 무관한 외부 사정
- 프롬프트 길이 변화 — 스토리 길이가 길어지면 컨텍스트가 커집니다
- 모델이나 프롬프트 버전 교체 — **manyak-ai 배포와 시각을 대조해 보세요**
- AI 컨테이너의 자원 부족 — 인프라 패널의 시스템 CPU와 함께 봅니다
- 같은 인스턴스에서 서버가 CPU를 점유하는 상황

**읽는 법** — `feature`별 선이 **함께 오르는지 따로 오르는지**가 핵심입니다. 전부 함께 오르면 AI 서버나 제공자 전체 문제이고, 하나만 오르면 그 기능의 프롬프트나 처리 경로 문제입니다.

`story_completion`이 180초에 근접하면 타임아웃 직전이라는 뜻입니다. 상한을 240초로 잡은 게 이걸 보기 위해서입니다 — **상한이 120초였다면 그 구간이 전부 뭉개져 보이지 않았을 것입니다.**

**함정** — `choice_generation`은 **현재 라인이 안 나오는 게 정상입니다.** 선택지가 채팅 턴 응답에 함께 오기 때문에 독립 AI 호출이 없습니다. legend에 나타나지 않는 `feature`는 계측 누락이 아니라 그 시간대에 호출이 없었다는 뜻입니다.

## AI 실패율 (feature별, %)

```promql
100 * sum by (feature) (
        rate(manyak_ai_call_duration_milliseconds_count{service_name="$service", outcome="failure"}[5m])
        or 0 * rate(manyak_ai_call_duration_milliseconds_count{service_name="$service"}[5m]))
    / clamp_min(sum by (feature) (rate(manyak_ai_call_duration_milliseconds_count{service_name="$service"}[5m])), 0.0001)
```

| | |
| --- | --- |
| 단위 | `percent` — 0~100 |
| 임계선 | 5% 주황 · 20% 빨강 |
| 분할 | `feature`별 |

**무엇을 보나** — AI 호출이 실패하는 비율입니다. **여기 `failure`는 전부 진짜 AI 실패입니다.** `AiCallRecorder`가 AI 호출만 감싸기 때문에 크레딧 부족이나 권한 거부 같은 게 섞일 여지가 없습니다. 스토리 완성 쪽 `outcome`과 다른 점입니다.

**값을 움직이는 것**

- LLM 제공자 장애나 rate limit
- 타임아웃 — 응답이 90초·180초를 넘긴 경우
- manyak-ai 컨테이너 다운이나 재시작 — **배포 중 짧게 튑니다**
- 응답 검증 실패 — AI가 200을 줬지만 서버가 스키마·내용 검증에서 깐 경우. **이건 Langfuse에서는 성공으로 보입니다**
- 네트워크 문제 — 같은 호스트라 드물지만 컨테이너 재시작 중 발생 가능

**읽는 법** — 배포 중 짧은 스파이크는 정상입니다. **지속적으로 5%를 넘으면 조사 대상**이고, 20%를 넘으면 그 기능이 사실상 동작하지 않는 상태입니다.

`feature`별로 보는 이유는 프롬프트 단위로 문제가 갈리기 때문입니다. `story_completion`만 실패율이 높다면 완성 프롬프트나 출력 스키마가 최근 변경과 어긋났을 가능성이 큽니다.

**함정 — 무장애가 `No data`로 보이지 않게 하는 장치가 들어 있습니다.** 실패가 하나도 없는 `feature`는 분자 시계열이 없어 그래프에서 사라집니다. `or 0 * rate(전체)`는 전체 호출률에 0을 곱해 **그 `feature` 라벨을 가진 0짜리 시계열**을 만듭니다. `vector(0)`을 쓰지 않는 이유는 `vector(0)`에는 라벨이 없어 `by (feature)` 그룹에 붙지 못하기 때문입니다.

# 스토리 완성

유스케이스 층입니다. AI 호출뿐 아니라 **소유권 확인, 크레딧 또는 게스트 한도 처리, 여러 테이블 저장**까지 포함한 기능 전체를 잽니다.

## 완성 p95 (ms)

```promql
# success
histogram_quantile(0.95, sum by (le) (rate(manyak_story_creation_duration_milliseconds_bucket{service_name="$service", outcome="success"}[5m])))
# failure
histogram_quantile(0.95, sum by (le) (rate(manyak_story_creation_duration_milliseconds_bucket{service_name="$service", outcome="failure"}[5m])))
```

| | |
| --- | --- |
| 단위 | `ms` — 밀리초 |
| 히스토그램 구간 | 100ms ~ 240s |
| 계열 | `success`와 `failure` 두 선 |

**무엇을 보나** — 사용자가 스토리 하나를 얻기까지의 실제 소요입니다. `story_completion` AI 호출보다 항상 **크거나 같습니다.**

**두 선을 나눠 그리는 이유** — 성격이 다릅니다. `success`는 제품 체감 성능이고, `failure`는 주로 **타임아웃까지 기다린 시간**이라 180초 근처에 붙습니다. 한 선으로 합치면 실패 비중이 변할 때마다 값이 출렁여 해석이 안 됩니다.

**값을 움직이는 것**

- `story_completion` AI 호출 시간 — **대부분을 차지합니다**
- 크레딧 선차감과 저장 트랜잭션
- 락 대기 — 같은 세션에 동시 요청이 겹치는 경우
- DB 커넥션 대기
- 저장할 데이터 양 — 스토리가 길수록 씁니다

**읽는 법 — AI p95와의 차이가 핵심 정보입니다.**

| 관측 | 해석 |
| --- | --- |
| AI p95 ↑ · 완성 p95 ↑ (비슷하게) | AI 지연이 그대로 전달되는 중. 우리가 할 게 없음 |
| AI p95 정상 · 완성 p95 ↑ | **AI 밖에서 시간을 쓰는 중** — 저장·크레딧·락 대기 의심 |
| 완성 `failure` p95가 180초에 붙음 | AI 타임아웃이 실패의 지배적 원인 |

**⚠️ 두 p95를 빼서 AI 밖 소요를 구할 수는 없습니다.** 서로 다른 표본에서 계산한 분위수라 산술이 성립하지 않습니다. "어느 쪽을 의심할지"까지만 좁히는 도구입니다.

**측정에서 일부러 뺀 것** — AI 호출 없이 저장된 결과만 돌려주는 두 경로는 제외합니다.

1. 멱등 재요청 — 같은 `requestId`로 다시 온 완료 요청
2. 회수 재실행 재구성 — 세션은 완료됐는데 요청 행이 미완료로 남은 경우

둘 다 밀리초짜리 조회라, 포함하면 수십 초짜리 생성과 섞여 **p95가 실제 비용보다 낙관적으로 왜곡됩니다.** 판별은 `aiCallLogId != null`로 합니다(KNK-784).

## 완성 결과 분포 (/s)

```promql
sum by (outcome) (rate(manyak_story_creation_duration_milliseconds_count{service_name="$service"}[5m]))
```

| | |
| --- | --- |
| 단위 | `ops` — 초당 건수. Y축 최소 0 |
| 분할 | `outcome` 3값 |

**무엇을 보나** — 지연이 아니라 **건수**입니다. 스토리 완성 시도가 어떤 결과로 끝나는지의 구성비를 봅니다.

**`outcome` 세 값의 뜻과 소요**

| 값 | 뜻 | 전형적 소요 | 무엇을 의미하나 |
| --- | --- | --- | --- |
| `success` | 생성·저장까지 완료 | 수 초 ~ 180초 | 정상 |
| `failure` | 생성을 **시도하다** 깨짐 | 수 초 ~ 180초 | AI 실패·타임아웃·저장 경합 |
| `rejected` | 생성 시도 **이전** 4xx 거부 | 밀리초 | 세션 없음·소유권·크레딧 부족·중복 |

**값을 움직이는 것**

- `success` — 실제 사용량. 제품 지표에 가깝습니다
- `failure` — AI 장애, 배포 중 재시작, 동시 요청 경합
- `rejected` — **클라이언트 쪽 사정으로 얼마든지 늘어납니다.** 프론트엔드 재시도 루프, 크레딧 소진 사용자의 반복 시도, 잘못된 세션 ID

**읽는 법 — `rejected`가 늘어난 것은 서버 장애가 아닙니다.** 오히려 서버가 제대로 막고 있다는 뜻입니다. 다만 급증한다면 프론트엔드 버그나 크레딧 정책 문제를 의심할 근거가 됩니다.

`failure`가 `success`에 비해 눈에 띄게 늘면 AI 실패율 패널을 봅니다. 거기가 깨끗한데 여기 `failure`만 늘었다면 **AI 밖의 저장·경합 문제**입니다.

**⚠️ 알림을 건다면 `failure`만 봐야 합니다.** `rejected`를 섞으면 누군가 없는 세션을 반복 호출하는 것만으로 AI 장애 알림이 울립니다. 실패 p95도 마찬가지로, 밀리초짜리 거부가 분포를 끌어내려 **AI가 실제로 느려지는데 지표는 개선된 것처럼 보이는 역전**이 생깁니다.

**분류 기준은 상태 코드가 아닙니다.** compile이 시작됐는지로 가릅니다 — 동시 요청이 겹쳐 AI 호출 뒤에 409가 나는 경우가 있는데, 상태 코드만 보면 수십 초 쓴 실패가 밀리초 거부로 잘못 분류됩니다(KNK-784).

**여기 없는 것** — 스토리**라인** 생성은 이 패널에 없습니다. 유스케이스 타이머가 완성에만 붙어 있어서입니다. 게스트 한도 소진(402)은 AI 호출 전에 거부되므로 Langfuse에도 안 남아, **현재 어디에서도 관측되지 않습니다.**

## 스토리라인 결과 분포 (/s)

```promql
sum by (outcome) (rate(manyak_storyline_creation_result_total{service_name="$service"}[5m]))
```

| | |
| --- | --- |
| 단위 | `ops` — 초당 건수. Y축 최소 0 |
| 분할 | `outcome` 3값 |
| 종류 | **Counter** — 히스토그램 버킷이 없어 시계열이 3개로 끝납니다 |

**무엇을 보나** — 스토리라인 생성 시도가 어떤 결과로 끝나는지입니다. 완성 쪽과 달리 **소요는 재지 않습니다.** 스토리라인은 AI 호출 1회가 유스케이스의 거의 전부라 duration이 `manyak_ai_call_duration{feature="storyline_generation"}`과 사실상 겹치기 때문입니다.

**⚠️ 이 패널이 존재하는 이유는 `rejected`입니다.** 게스트 사용 한도가 소진되면 402로 거부되는데, 이 거부는 **AI 호출 이전**(`reserveForGuestOrNull`)에 끊깁니다. 그래서 AI 타이머에도 안 잡히고 AI를 부르지 않았으니 Langfuse trace도 없습니다. **다른 어디에서도 관측되지 않는 유일한 구간입니다**(KNK-801).

**`outcome` 값의 뜻**

| 값 | 뜻 | 무엇을 의미하나 |
| --- | --- | --- |
| `success` | 스토리라인 생성·저장 완료 | 정상 |
| `failure` | AI 호출 **진입 후** 깨짐 | AI 실패(502)·타임아웃·저장 실패 |
| `rejected` | AI 호출 **이전** 4xx 거부 | **게스트 한도 소진(402)**·사용할 수 없는 태그 ID(400) |

**값을 움직이는 것**

- `success` — 실제 사용량. 제품 지표에 가깝습니다
- `failure` — AI 장애, 배포 중 재시작. AI 실패율 패널의 `storyline_generation`과 같이 움직여야 정상입니다
- `rejected` — **게스트 한도 소진이 지배적입니다.** 늘어난다면 비회원 유입이 늘었거나 한도 정책이 빡빡하다는 신호이지 서버 장애가 아닙니다

**읽는 법** — `rejected` 급증은 장애가 아니라 **제품 신호**입니다. 한도에 막힌 게스트가 많다는 뜻이므로 가입 전환 흐름이나 한도값을 다시 볼 근거가 됩니다. 반면 `failure`가 늘면 AI 실패율 패널을 봅니다. 거기가 깨끗한데 여기 `failure`만 늘었다면 AI 밖의 저장 문제입니다.

**측정에서 빠지는 것** — 멱등 재요청(같은 `requestId` replay)은 콜백 자체가 실행되지 않아 자연히 제외됩니다. 완성 경로와 달리 스토리라인에는 회수 재실행 재구성이 없어 별도 판별이 필요 없습니다.

**⚠️ 수신 이름 미확인** — 코드의 `manyak.storyline.creation.result`는 Prometheus 규약상 Counter라 `_total`이 붙습니다. 다만 **OTLP를 거친 실제 수신 이름은 아직 실측하지 않았습니다.** 타이머가 `_seconds`에서 `_milliseconds`로 바뀐 전례가 있으니, 배포 후 Metrics browser에서 확인하고 다르면 이 쿼리를 고치세요. 틀리면 오류가 아니라 **빈 패널**이 됩니다.

# 인프라 — CPU · 힙 · GC · DB 커넥션

운영은 **`t3.small` 한 대(2 vCPU · 2GB)에 server와 ai 컨테이너가 함께** 떠 있습니다. 자원 경합이 실재하는 가설이므로, "외부 AI가 느린 것"과 "자원이 없어 느린 것"을 가르기 위해 같은 화면에 둡니다.

## CPU 사용률

```promql
process_cpu_usage{service_name="$service"}   # 프로세스
system_cpu_usage{service_name="$service"}    # 시스템
```

| | |
| --- | --- |
| 단위 | `percentunit` — **0~1 비율**(Grafana가 %로 표시). Y축 0~1 고정 |
| 출처 | Micrometer 기본 바인더. `rate` 없이 게이지를 그대로 |

**두 선의 차이가 이 패널의 핵심입니다.**

| 계열 | 무엇 |
| --- | --- |
| `프로세스` | **이 JVM**이 쓰는 CPU |
| `시스템` | **호스트 전체** — AI 컨테이너와 OS를 포함 |

**읽는 법 — 시스템이 높은데 프로세스가 낮으면 우리 서버가 아니라 이웃이 CPU를 먹는 중입니다.** t3.small에 AI 컨테이너가 같이 있으므로 대개 그쪽입니다. 이때 응답이 느려도 서버 코드를 뒤질 일이 아닙니다.

둘 다 높으면 실제 부하이고, 프로세스만 높으면 우리 쪽 문제(무한 루프, 과도한 직렬화, GC)입니다.

**값을 움직이는 것**

- AI 컨테이너의 추론 부하 — 시스템만 올립니다
- 요청 급증 — 둘 다 올립니다
- GC — 프로세스 CPU를 올립니다. GC 패널과 같이 보세요
- 배포 직후 JIT 컴파일과 클래스 로딩 — **기동 수 분간 높은 게 정상입니다**

**⚠️ t3는 버스트 인스턴스입니다.** CPU 크레딧이 소진되면 baseline(t3.small은 20%)으로 제한되어, **부하가 그대로인데 갑자기 느려지는** 현상이 생깁니다. 이 패널만으로는 크레딧 소진을 알 수 없으므로, CPU가 20% 근처에서 평평하게 눌려 있으면 CloudWatch의 `CPUCreditBalance`를 확인해야 합니다.

## JVM 힙

```promql
sum(jvm_memory_used_bytes{service_name="$service", area="heap"})       # used
sum(jvm_memory_committed_bytes{service_name="$service", area="heap"})  # committed
```

| | |
| --- | --- |
| 단위 | `bytes` — Grafana가 MB/GB로 자동 표시 |
| 필터 | `area="heap"` — non-heap(메타스페이스·코드캐시) 제외 |
| 집계 | `sum` — Eden·Survivor·Old 등 여러 풀의 합 |

**두 선의 뜻**

| 계열 | 무엇 |
| --- | --- |
| `used` | 실제로 객체가 점유한 양. **톱니 모양이 정상**입니다 |
| `committed` | JVM이 OS에서 확보해 둔 양. 계단식으로 변합니다 |

**읽는 법 — `used`의 톱니는 건강한 신호입니다.** 올라갔다가 GC로 떨어지는 게 정상 동작입니다. **위험한 모양은 톱니의 골짜기가 계속 높아지는 것**입니다. GC를 해도 회수되지 않는 객체가 쌓인다는 뜻이라 누수를 의심합니다.

`used`가 `committed`에 계속 붙어 있으면 힙이 부족한 상태입니다. GC 패널에서 pause가 함께 늘고 있을 겁니다.

**값을 움직이는 것**

- 요청량 — 요청당 할당이 쌓입니다
- 스토리 본문처럼 **큰 문자열**을 다루는 작업 — 완성 응답은 크기가 상당합니다
- 캐시나 컬렉션 누수
- GC 알고리즘과 힙 설정 — 컨테이너 메모리 제한에서 자동 산정됩니다

**⚠️ 2GB 인스턴스에 컨테이너 두 개가 있습니다.** 힙 상한이 넉넉해 보여도 호스트 전체로는 빠듯합니다. 여기서 안 보이는 실패 모드가 **OOM Killer에 의한 컨테이너 강제 종료**인데, 그러면 이 패널은 값을 남기지 않고 그냥 끊깁니다.

## GC pause 평균 (ms)

```promql
sum(rate(jvm_gc_pause_milliseconds_sum{service_name="$service"}[5m]))
  / clamp_min(sum(rate(jvm_gc_pause_milliseconds_count{service_name="$service"}[5m])), 0.0001)
```

| | |
| --- | --- |
| 단위 | `ms` — 밀리초 |
| 통계 | **평균**(p95 아님) |

**무엇을 보나** — GC 한 번이 애플리케이션을 얼마나 멈추는지입니다. GC 정지 동안은 요청 처리가 멈추므로 **모든 엔드포인트의 응답시간에 직접 더해집니다.**

**p95가 아니라 평균인 이유** — 이 메트릭에 percentile histogram을 켜지 않아 `_bucket` 시계열이 없습니다. `_sum / _count`로 평균만 계산할 수 있습니다. 켜지 않은 이유는 GC 정지가 힙 패널과 함께 보면 충분히 판단되는 보조 지표라, 버킷을 추가할 만큼 예산을 쓸 값어치가 없어서입니다.

**값을 움직이는 것**

- 힙 압박 — 여유가 없을수록 자주, 오래 멈춥니다
- 큰 객체의 잦은 할당
- CPU 부족 — GC 스레드도 CPU를 씁니다. **AI 컨테이너와의 경합이 GC를 늘릴 수 있습니다**

**읽는 법** — 수 밀리초대는 정상입니다. **수백 밀리초가 지속되면 HTTP p95에 그대로 반영됩니다.** 힙 패널의 `used`가 상한에 붙는 시각과 겹치는지 확인하세요.

**함정 — 기동 직후 빈 패널은 정상입니다.** GC가 실제로 한 번은 발생해야 시계열이 생깁니다. 트래픽이 적으면 한참 비어 있을 수 있습니다.

## HikariCP 커넥션

```promql
sum(hikaricp_connections_active{service_name="$service"})   # active
sum(hikaricp_connections_idle{service_name="$service"})     # idle
sum(hikaricp_connections_pending{service_name="$service"})  # pending
```

| | |
| --- | --- |
| 단위 | `short` — 개수 |
| 출처 | HikariCP 바인더. 풀 크기는 Spring Boot 기본값(최대 10) |

**세 계열의 뜻**

| 계열 | 무엇 | 정상 |
| --- | --- | --- |
| `active` | 지금 쿼리 중인 커넥션 | 부하에 따라 오르내림 |
| `idle` | 대기 중인 여유 커넥션 | 여유가 있으면 0보다 큼 |
| `pending` | **커넥션을 못 얻어 기다리는 스레드** | **항상 0이어야 함** |

**읽는 법 — `pending`이 0이 아니면 그것만으로 DB 병목 신호입니다.** 다른 해석의 여지가 없습니다. 풀이 다 찼고 요청 스레드가 줄을 선 상태이며, 이 대기는 HTTP p95에 그대로 더해집니다.

`active`가 최대치(10)에 붙어 있고 `idle`이 0이면 `pending`이 뜨기 직전입니다.

**값을 움직이는 것**

- 느린 쿼리 — 커넥션을 오래 붙잡습니다
- 긴 트랜잭션 — **특히 트랜잭션 안에서 AI를 호출하면 최악입니다.** 커넥션을 수십 초 점유합니다
- 동시 요청 급증
- 커넥션 누수 — `active`가 부하와 무관하게 계속 높으면 반납되지 않는 것입니다

**⚠️ `jdbc_connections_*`도 같은 값을 다른 이름으로 내보냅니다.** 둘 다 쿼리하면 시계열만 두 배로 쓰고 정보는 같습니다. 이 대시보드는 `hikaricp_*`만 씁니다.

# 예산 — 무료 티어 한도 감시

서비스 지표가 아니라 **비용 안전장치**입니다.

## Active series (무료 티어 한도 10,000)

```promql
grafanacloud_instance_active_series
```

| | |
| --- | --- |
| 단위 | `short` — 개수 |
| 임계선 | 7,000 주황 · 9,000 빨강 |
| **데이터소스** | **`usage_datasource`** — 메트릭 데이터소스가 아닙니다 |

**무엇을 보나** — Grafana Cloud가 저장 중인 활성 시계열 수입니다. 무료 티어 한도는 10,000입니다.

**⚠️ 이 패널만 데이터소스가 다릅니다.** `grafanacloud-usage`를 골라야 뜹니다. 두 데이터소스가 **둘 다 Prometheus 타입**이라 변수가 엉뚱한 쪽을 집으면 이 패널만 조용히 비고, 그래서 변수에 regex 필터를 걸어 뒀습니다(README 참고).

**왜 대시보드에 두나 — 트라이얼 동안은 한도가 안 걸립니다.** 넘겨도 아무 증상이 없다가 **만료 시점에 데이터가 잘리기 시작하고**, 그때 원인을 찾기가 까다롭습니다. 관측이 조용히 죽는 것을 관측으로 막는 장치입니다.

**값을 움직이는 것 — 트래픽이 아닙니다.**

시계열은 **라벨 조합 수**로 늘어납니다. 앰플리튜드 기준 피크(9,937 이벤트/일)와 평상시(약 750)가 13배 차이인데 시계열 수는 거의 같았습니다.

실제로 늘리는 것은 다음입니다.

| 원인 | 영향 |
| --- | --- |
| **엔드포인트 추가** | 하나당 50~150 — **가장 큰 요인** |
| 새 `feature`나 `outcome` 값 | 태그 값 하나당 버킷 수만큼 |
| 히스토그램 상한·구간 변경 | 버킷 수가 바뀌면 전체에 곱해짐 |
| 처음 호출된 엔드포인트 | **존재가 아니라 호출이 시계열을 만듭니다** |
| 고유값 태그 실수 | `user_id`·`story_id` 등 — 무한히 늘어남 |

**읽는 법 — 절대값보다 기울기입니다.** 평평하면 정상 상태이고, 계단식으로 오르면 배포로 엔드포인트가 늘었다는 뜻입니다. **완만하게 계속 오르면 고유값 태그가 섞여 들어간 것을 의심해야 합니다.**

2026-08-06 배포 1시간 후 실측은 약 1,200이었습니다(사전 추정 5,500의 약 1/4.5). 다만 각 엔드포인트가 처음 호출될 때마다 늘어나므로 **아직 정상 상태가 아닙니다.** 며칠 지나 평탄해진 값을 봐야 하고, 그때 README의 예산 표를 갱신하세요.

**갱신 주기가 느립니다.** 사용량 지표는 서비스 지표와 달리 수 분 단위로 갱신되므로, 방금 배포한 변경이 즉시 반영되지 않습니다.

**한도에 근접하면** 순서대로 씁니다. 1) HTTP 히스토그램 상한 10s → 3s (약 700 절감), 2) HTTP 히스토그램을 끄고 클라이언트 계산 p95 사용 (약 4,600 절감 — 단일 인스턴스라 시간 구간 재집계 손실이 실질적으로 없음).

# 아직 이 대시보드가 못 보는 것

| 없는 것 | 왜 | 어디서 보나 |
| --- | --- | --- |
| 요청별 구간 분해 | p95끼리 빼는 산술이 성립하지 않음 | 트레이스나 `request_id` 기반 별도 계측 필요 |
| 개별 사건 추적 | 메트릭에 고유값 태그를 넣지 않음 | 구조화 로그, `ai_call_logs`, Sentry |
| 토큰·비용·프롬프트 내용 | 카디널리티 폭발 | Langfuse |
| 스토리라인 생성 소요 | AI 호출 1회가 거의 전부라 AI 타이머와 겹침 | AI 호출 p95의 `storyline_generation` |
| 알림 | 기준선이 없어 임계값이 근거 없는 숫자가 됨 | KNK-800에서 설계 예정 |
| CPU 크레딧 잔량 | Micrometer가 수집하지 않음 | CloudWatch `CPUCreditBalance` |
| 컨테이너 OOM kill | JVM이 죽으면 기록이 안 남음 | EC2 `dmesg`, 컨테이너 재시작 로그 |
