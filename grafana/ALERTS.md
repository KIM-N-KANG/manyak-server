# 알림 규칙 — Grafana Cloud

대시보드가 "보러 가는" 도구라면 알림은 "찾아오는" 도구입니다. 그래서 판단 기준이 다릅니다. 대시보드 패널은 궁금하면 보면 그만이지만, **알림은 울린 뒤 내가 지금 할 행동이 없으면 그 자체가 손해**입니다. 무뎌지고, 무뎌진 알림은 진짜 장애 때도 안 봅니다.

규칙을 3개로 끊은 게 이 문서의 핵심 결정입니다. 설계 배경과 쿼리 규칙은 [`README.md`](./README.md), 패널별 해석은 [`PANELS.md`](./PANELS.md)에 있습니다.

## 규칙 3개

전부 `service_name="manyak-server"` 필터가 붙습니다. 평가 주기는 1분(수집 step과 같음).

| # | 규칙 | 조건 | pending | No Data |
| --- | --- | --- | --- | --- |
| 1 | 수집 끊김 | 절대 참이 안 됨 | 10m | **Alerting** |
| 2 | AI 실패 급증 | `> 5` | 0 | OK |
| 3 | 환불 실패 | `> 0` | 0 | OK |

### 1. 수집 끊김 = 서버 다운

```promql
sum(rate(http_server_requests_milliseconds_count{service_name="manyak-server"}[5m]))
```

**임계 조건은 `IS BELOW 0`으로 둡니다 — 절대 참이 되지 않습니다.** 이 규칙은 값을 보지 않고 **값이 오는지만** 봅니다. 데이터가 끊기면 No Data가 되고, No Data가 Alerting으로 매핑되면서 발화합니다.

이 쿼리를 고른 이유는 **절대 비지 않는 시계열**이기 때문입니다. ALB 헬스체크가 주기적으로 들어오므로 사용자 트래픽이 0인 새벽에도 바닥값이 깔립니다(`PANELS.md` 요청률 패널). 즉 여기가 비었다는 건 트래픽이 없다는 뜻이 아니라 **서버 또는 OTLP push가 죽었다**는 뜻입니다.

둘을 구분하지 못하지만 상관없습니다. 어느 쪽이든 사람이 인스턴스를 봐야 합니다.

**pending 10분은 배포 때문입니다.** `deploy.sh`가 컨테이너를 교체하면 push가 몇 분 끊깁니다. 이게 없으면 릴리스마다 알림이 울리고, 그러면 곧 아무도 안 봅니다. 대가는 진짜 다운을 10분 늦게 아는 것인데, 자동 복구 수단이 없는 단일 인스턴스라 어차피 사람이 손으로 붙어야 하고 10분 차이가 대응을 바꾸지 않습니다.

**pending이 No Data 전이에도 적용되는지는 자명하지 않아 실측했습니다**(2026-08-09). pending을 1분으로 낮추고 강제 No Data를 만들자 저장 1분 30초 뒤에 Slack이 도착했습니다 — pending 1분 + 기본 group wait 30초입니다. 적용되지 않았다면 즉시 왔을 것이고, 그랬다면 배포를 막을 다른 수단(창을 `[15m]`으로 늘리는 등)이 필요했습니다.

발화 직전 몇십 초 동안 규칙 상태가 `Inhibited`로 표시됐지만 알림은 정상적으로 나갔습니다. **이 뱃지만 보고 알림이 죽었다고 판단하지 마세요.**

### 2. AI 실패 급증

```promql
sum(increase(manyak_ai_call_duration_milliseconds_count{service_name="manyak-server", outcome="failure"}[10m]))
```

10분 동안 AI 호출 실패가 5건을 넘으면 발화합니다.

**`feature`별로 쪼개지 않습니다.** 알림이 답해야 하는 질문은 "AI가 지금 망가졌나" 하나이고, 어느 기능인지는 울린 뒤 대시보드에서 봅니다. 쪼개면 규칙 4개가 되고 같은 장애에 4번 울립니다.

`AiCallRecorder`가 AI 호출만 감싸므로 여기 `failure`에는 크레딧 부족이나 권한 거부가 섞일 여지가 없습니다 — 전부 진짜 AI 실패입니다. `outcome`이 2값인 유일한 메트릭이라 `rejected` 배제를 따로 신경 쓸 필요도 없습니다.

**능동 헬스체크를 따로 두지 않는 이유** — AI 서버가 죽었는데 호출이 없으면 사용자 영향도 없습니다. 첫 사용자가 실패하는 순간 이 규칙이 잡습니다. 프로버를 하나 더 띄워 운영할 값어치가 없습니다.

### 3. 환불 실패

```promql
sum(increase(manyak_chat_turn_refund_total{service_name="manyak-server", outcome="failure"}[10m]))
```

**0이 아니면 발화합니다.** 다른 규칙과 성격이 다릅니다 — 이건 장애 신호가 아니라 **정산 정확성 신호**입니다. 되돌리지 못했다는 것은 사용자가 실패한 턴에 대해 과금된 채 남았다는 뜻입니다(`PANELS.md` 환불 패널).

임계값이 0인 알림은 보통 위험하지만 여기서는 안전합니다. 정상 운영에서 이 값은 0이고, 0이 아닌 순간이 곧 조사 대상입니다. 울리면 그 시각의 `chat_turn_refund_failed` 로그에서 `idempotency_key`와 `chat_pk`를 찾아 원장과 대조합니다.

**⚠️ 이 규칙은 서버의 카운터 사전 등록에 의존합니다.** Micrometer Counter는 첫 `increment()` 때 등록되므로, 사전 등록이 없으면 첫 실패가 값 1인 샘플 하나로 등장하고 `increase()`가 뺄 이전 샘플을 못 찾아 결과를 내지 못합니다. 규칙은 그것을 No Data로 보고 `Normal`로 넘깁니다 — **첫 한 건을 잡으려던 규칙이 정확히 그 한 건을 놓칩니다.**

`ChatTurnRefundMeters`가 기동 시 `success`·`failure`를 0으로 등록해 이 사각지대를 없앱니다. **이 빈을 지우면 알림이 조용히 반쪽이 됩니다** — 규칙은 초록으로 남고 첫 실패만 사라지므로 알아차릴 방법이 없습니다. 회귀 가드는 `ChatTurnRefundMetersTests`와 `ChatTurnCreditRefundIntegrationTests`의 "환불 실패 카운터는 실패가 한 번도 없어도 등록돼 있다"입니다.

같은 함정이 임계값 0인 다른 규칙에도 적용됩니다. **알림이 카운터의 첫 한 건에 의존한다면 그 카운터는 사전 등록돼야 합니다.** 규칙 2는 임계값이 5라 첫 건이 보이지 않아도 발화 시점에는 시계열이 이미 존재하므로 영향이 없습니다.

## 왜 비율이 아니라 건수인가

티켓(KNK-800) 초안은 5xx 오류율·AI 실패율처럼 **비율** 임계값을 후보로 뒀는데, 지금 트래픽에서는 쓸 수 없습니다.

새벽에 요청이 5건 들어와 1건이 실패하면 오류율은 20%입니다. 대시보드에서는 "요청률 패널과 함께 보라"는 주의로 충분하지만, 알림은 사람이 그 맥락을 볼 수 없는 상태에서 울립니다.

건수 기준은 이 문제가 없습니다. **덤으로 티켓의 선행 조건도 사라집니다** — 비율 임계값을 정하려면 평일·주말·캠페인 유무별 기준선이 며칠 쌓여야 했지만, "10분에 5건"은 기준선 없이도 말이 됩니다.

회의에서 멘토가 "몇 초 동안 400이나 500 에러 몇 번 이상"이라고 건수로 말한 것과 같은 판단입니다. 다만 **창 크기는 10초가 아니라 10분입니다** — OTLP export step이 60초라 원본 데이터 포인트가 분당 하나뿐이고, 1분 미만 사건은 애초에 관측되지 않습니다.

## No Data를 규칙 1에만 몰아준 이유

**서버가 내려가면 모든 규칙이 동시에 No Data가 됩니다.** 전부 Alerting으로 두면 장애 하나에 알림 3개가 옵니다. 전부 OK로 두면 서버가 죽어도 아무도 모릅니다. 로컬 실습 때 후자를 피하려다 규칙 전체를 Pause했던 이력이 있습니다.

그래서 **No Data를 발화 신호로 쓰는 규칙을 하나만 둡니다.**

| | 규칙 1 | 규칙 2 · 3 |
| --- | --- | --- |
| 데이터 없음의 뜻 | **서버가 죽었다** | 그 사건이 안 일어났다 |
| No Data 동작 | Alerting | OK |

규칙 2·3의 쿼리는 실패가 한 건도 없으면 분자 시계열이 아예 없어 `increase()`가 빈 벡터를 냅니다. **무장애 상태가 곧 No Data입니다.** 그래서 여기서 No Data를 발화시키면 평온한 새벽마다 울립니다.

대시보드 패널은 이걸 `or vector(0)`으로 메워 "0"과 "수집 실패"를 눈으로 구분하지만, **알림 규칙에는 쓰지 않습니다.** 0을 채워 넣으면 조건(`> 5`, `> 0`)이 정상적으로 거짓이 되어 결과는 같고, 대신 수집이 끊겨도 규칙이 조용해집니다. 그 공백은 규칙 1이 덮습니다.

## 일부러 뺀 것

| 뺀 것 | 이유 |
| --- | --- |
| 5xx 오류율 | AI 실패가 502로 나가므로 규칙 2와 같은 사건을 두 번 울립니다. 남는 건 AI 밖 500인데 드뭅니다 |
| AI 호출 p95 | 외부 의존이라 새벽에 울려도 할 행동이 없습니다. 느려진 건 대시보드에서 봅니다 |
| 스토리 완성 실패율 | 실패 원인의 대부분이 AI라 규칙 2에 흡수됩니다 |
| active series 한도 | 하루 단위로 움직이는 값이라 알림보다 주기적 확인이 맞습니다. 대시보드에 임계선(7,000·9,000)이 이미 있습니다 |
| 야간 mute timing | 규칙이 3개뿐이라 야간 발화 자체가 드뭅니다. 조용히 하고 싶으면 Slack 채널 알림 설정이 이미 그 기능입니다 |

**AI 실패의 상당수는 AI 응답 JSON 형식 오류(502)입니다.** 일회성이고 재시도로 풀리므로 개별 건은 알림 대상이 아닙니다 — 규칙 2의 임계값 5가 "일회성"과 "지금 계속 깨지는 중"을 가르는 선입니다.

## 임계값에는 근거가 없습니다

`5`와 `10m`은 관측에서 나온 숫자가 아니라 **일단 시작하기 위한 숫자**입니다. 이 사실을 문서에 남기는 이유는, 근거 있는 숫자로 오해하고 그대로 두는 게 가장 나쁘기 때문입니다.

조정 절차는 하나뿐입니다. **운영에서 실제로 몇 번 울리는지 보고 조입니다.**

- 주 1회 이상 오발화 → 임계값을 올리거나 창을 늘립니다
- 장애를 겪었는데 안 울렸다 → 임계값을 내립니다
- 몇 주 동안 한 번도 안 울렸다 → 정상일 수도 있고 규칙이 죽었을 수도 있으므로 아래 발화 테스트를 다시 합니다

## 발화 테스트

**규칙을 만든 직후 반드시 한 번 울려 봅니다.** 알림의 유일한 실패 모드는 조용히 안 오는 것이고, 그건 진짜 장애 때 알게 됩니다.

가장 싼 방법은 임계값을 잠깐 뒤집는 것입니다.

1. 규칙 2의 조건을 `> 5` → `>= 0`으로 바꿔 저장
2. Slack 채널에 알림 도착 확인 (1~2분)
3. 조건을 되돌리고, 해제(Resolved) 알림까지 오는지 확인

규칙 1은 조건이 아니라 No Data 경로로 발화하므로 위 방법으로는 검증되지 않습니다. **쿼리의 `service_name`을 존재하지 않는 값으로 잠깐 바꾸면** 강제로 No Data가 됩니다. pending 10분을 기다려야 하므로 이때 pending을 1분으로 함께 낮췄다가 되돌립니다.

**Resolved는 5분쯤 늦게 옵니다.** 발화는 group wait 30초 뒤 바로 나가지만 해제는 group interval 5분 tick에 묶입니다(2026-08-09 실측: 두 규칙 모두 발화 → 해제가 정확히 5분). 원복했는데 해제 알림이 안 온다고 실패로 판단하지 마세요.

## 채널

공개 채널 **`#그라파나-알림`** 과 전용 incoming webhook을 씁니다. 팀 채널 명명 규칙(`센트리-데일리-리포트`·`앰플리튜드-데일리-리포트`·`피드백-알림`)을 따라 도구명은 한글로, 접미사는 성격으로 씁니다 — `-리포트`는 정기 요약, `-알림`은 사건이 생길 때만 오는 푸시입니다.

**피드백 webhook(`MANYAK_SLACK_FEEDBACK_WEBHOOK_URL`)을 재사용하지 않습니다.** Slack incoming webhook은 채널이 고정이라 재사용하면 같은 채널에 섞이고, 피드백(좋은 소식) 사이에 장애(나쁜 소식)가 묻힙니다.

**`#센트리-데일리-리포트`와도 겹치지 않습니다.** 센트리는 예외 단위로 쌓아 하루치를 요약하고, 규칙 2는 "10분에 5건"이라는 빈도 판정입니다. 상시 발생하는 AI 응답 JSON 형식 오류(502)는 센트리에 매번 남지만 여기서는 조용합니다 — 그게 의도입니다.

라벨과 알림 정책은 두지 않습니다. 수신자가 한 명이고 채널이 하나라 라우팅할 게 없어, 기본 정책이 세 규칙을 그대로 그 채널로 보냅니다.

## 이 파일이 레포에 있는 이유

**알림 쿼리는 서버 코드가 정의한 메트릭 이름과 라벨에 의존합니다.** 대시보드를 이 레포에 둔 것과 같은 이유이고, 알림 쪽이 오히려 더 급합니다 — 계약이 바뀌면 대시보드는 빈 패널로 눈에 띄지만 **알림은 조용히 안 울리는 상태가 됩니다.**

메트릭 이름·`outcome` 값·`service_name`을 바꾸는 PR은 `alerts.yaml`도 함께 고쳐야 합니다.

`alerts.yaml`은 Grafana UI에서 만든 규칙을 export한 것입니다(그룹 화면의 `Export`). 손으로 먼저 쓰지 않는 이유는 규칙 UID와 A/C 표현식 모델 보일러플레이트를 사람이 정확히 재현할 이유가 없어서입니다. 규칙을 UI에서 고쳤으면 다시 export해 이 파일에 반영합니다 — 대시보드 JSON과 같은 흐름입니다.

**contact point는 export에 포함되지 않습니다.** 규칙에는 `notification_settings.receiver`로 이름만 남고 webhook URL은 빠지므로, 이 파일은 비밀값을 담지 않습니다. contact point 자체는 UI에서만 관리합니다.

### YAML 읽는 법

UI 화면과 필드 이름이 달라 대조가 필요합니다.

| YAML | UI |
| --- | --- |
| `evaluator.type: lt` · `params: [0]` | `IS BELOW 0` |
| `evaluator.type: gt` · `params: [5]` | `IS ABOVE 5` |
| `for: 10m` | Pending period. **없으면 `None`** |
| `noDataState: OK` | No data → `Normal` |
| `relativeTimeRange.from: 600` | 쿼리 창 `10m to now` |

`datasourceUid: grafanacloud-prom`은 스택별 난수 UID가 아니라 Grafana Cloud가 주는 고정 별칭이라, 다른 스택에 import해도 그대로 붙습니다.
